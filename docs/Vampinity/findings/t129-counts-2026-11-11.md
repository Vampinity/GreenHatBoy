# T129 count-mode runs (11 Nov 2026, batch t129-counts)

> **Found:** The count-mode runs showed the stale-backing fix has nothing to fix on the forest exit and the decode cap acts lightly there; the door script ran on the wrong save, so the door part tested nothing.
>
> **So:** Park the stale-backing fix as count-only, and pair each script with its own save in the queue.

Batch: `eglantine-logs-2026-11-05/auto-20261111-205320-batch-t129-counts` (queue `queue-t129a.json`,
item `t129-counts`). Build T129 (459882d), eboot sha a1c04137bdaea79f, same eboot as the t129-prep-door batch an
hour earlier. Two runs, no control (count modes change nothing, so there is nothing to compare against).

Both env.txt files checked: `EDEN_UP_STALE_BACKING_FIX_VERIFY=1` and `EDEN_UP_ASTC_PENDING_STATS=1` in both, the
fix itself (`EDEN_UP_STALE_BACKING_FIX`) absent in both. Other differences between the two runs: run1194 also had
`EDEN_UP_AHEAD_GUARD=3`, `EDEN_UP_LIVE_SWITCHES=1`, `EDEN_GPU_TIME=1` (the door plan's live-schedule env);
run1195 had `EDEN_UP_FRITCHII_USAGE_TRACKER=1` and no frame-ahead guard. Both had `EDEN_NX2_FRAMES_AHEAD=1`.

Terms, one line each:
- 102 = the game's "destroy this GPU memory" call. The stale-backing fix adds work there.
- Decode image = the temporary picture a compressed (ASTC) texture is unpacked into on the GPU before it is
  packed again in a format the PS5 reads.
- Decode cap = our rule that, while memory is short, waits for the GPU to finish old decode images once more
  than 64 MiB of them are in flight.
- Script clock = seconds from the game's start (the script's marks); app clock = the log's seconds.
  Offset per run from runs.jsonl: run1194 +17.98 s, run1195 +27.03 s (cold boot).

## 1. Why run1194 stopped: the wrong save, not the build

**The door script ran on the forest-exit save.** The game was simply somewhere else.

- The queue item `t129-counts` puts back `owner-play-before-session1-20261111-0533` for the whole batch
  (queue-t129a.json, batch.log 20:53:38). That is the forest-exit save: it loads with Link outside on the hill.
  The door script needs the house save (`ocarina-owner-after-handplay-2026-11-08`), which the prep-door batch
  used (its batch.log 20:17:38). A queue item has one save, and this batch mixed a door run and an exit run.
- Script trace (result.json): title WAIT met (line 19, 46.4 s), load screen WAIT met (line 22, 48.4 s), load
  screen gone (line 29, 53.5 s), then **line 31 timed out**: `0 WAIT 60 LOOK 390 917 215 35 ...`, the wait for
  the "Move (L) Change View (R)" hint that shows at the first moment of control in the house. Best score 25
  of 120 looks, timeout at script 113.45 s (app ~131 s). The harness stopped the script and ended the test 45 s
  later (batch.log 20:55:54 and 20:56:41).
- In all six prep-door runs (run1188-1193, same build) the same line was met at script 74.5-75.7 s with
  score 99, and the door WAIT (line 38) at 78.6-79.8 s. All six ended `script_end`.
- Frames (`run1194-.../frames`, every 5 s): title, load screen, black load, then from about 20:55:07 to
  20:56:42 Link standing still on the grassy hill outside with hearts, the item buttons and the fairy on screen.
  That is the same spot run1195's first gameplay frames show. No hint text, no house. Link never moves (the
  script was blocked at the WAIT, so no stick input). After 20:56:47 the PS5 home screen (normal app quit).

**Not a freeze, hang or crash:**
- Game kept running to the end: present #5400 at app 168 s, 5 s fps lines steady at 30.5-31.3 fps to app 180 s
  (worst frame 39-43 ms per 5 s window), FETCH_COUNT lines every 10 s to app 178 s.
- No GPU wait or hang-watch line, no crash report (crash-index lists only older crashes from the night before).
- Error lines are the same as every healthy run: 16 "Unmapped Device ReadBlock" and 3 `<Critical>` lines in
  run1194, in run1195, and in each of the six prep-door runs.
- The app answered test-quit and closed normally (batch.log 20:56:50).

**Not related to either count mode.** The stop is a picture match that could never succeed from that save. The
check-mode page walk (the review's timing note) did not slow anything visible: 31 fps standing on the hill. The
stale-backing counter lines were normal (section 2).

**Console left healthy.** run1195 started 20:57:10 and ran its full route; the next batch (t129-heap,
run1196-1200 so far) started 21:02:47 and its runs end `Script done` one after another.

Totals run1195: 1,549 decodes, 19 made to wait, 30 GPU waits, 51 ms of waiting in all; the worst window 23 ms
(spread over 5 waits, so no single hitch of that size is proven). max_in_flight for the session 733 MiB.

Reading:
- **The cap does act**, at every load stretch of the forest exit, but lightly: 0-3 waits per 10 s after the
  first window, single-digit to 23 ms of waiting per window. Its 64 MiB limit holds: every window with
  short = decodes peaks at 25-63 MiB, except the 191 MiB one, which is one texture larger than the cap (the cap
  always keeps one; that texture is 0516's job, as the notes say).
- **The 733 MiB pile is the upstream case, and our cap missed it.** In the 70-80 s window 83 of 265 decodes ran
  while the cap's memory probe said "not short", and only then can the after-wait peak pass the cap. So up to
  733 MiB of decode images were held at once, with the cap switched off. The memory census in the same seconds
  (stderr, every 2 s) shows the largest free block at 341-714 MiB and decode_in_flight only 1-24 MiB at its
  samples. So the pile was short-lived and fell between samples. No crash or refusal followed in this run.
  Open question: the census says memory was "low" (largest block under 768 MiB) all through that window, but
  the cap's own probe said "not short" for 83 decodes. Its threshold is a different measure (the review says
  about 1 GiB of largest block, off again at 1.5 GiB). Worth one look at `graphics_memory_probe` before
  deciding anything.
- The save load itself is small: 21 decodes, 11 MiB, in both runs. The burst comes when Link starts moving
  on the hill.

## Verdict

1. **run1194's stop:** a script WAIT (line 31, the movement hint in the house) timed out because the batch put
   back the forest-exit save. The game was healthy on the hill at 31 fps. No freeze, hang or crash, and nothing
   to do with either count mode. The console stayed healthy (run1195 and the heap batch ran normally).
2. **Stale-backing fix:** nothing to fix on the forest exit. 868 destroys, 0 other GPU ranges, 0 tiles, 0 stale
   heap pages, 0 verify failures. The door load is still unmeasured. **Park the fix arm for the exit route**;
   decide for good after one door count run. If that is also all zero on the three counts that matter (other
   ranges, tiles, stale pages), park the switch with the reason "count-only on door load + forest exit,
   frame-ahead on: 0 ranges, 0 tiles, 0 stale heap pages; the test saw only those two loads".
3. **Decode cap:** it acts on the forest exit (19 waits, 51 ms in a run), never at the save load. The one real
   finding is a 733 MiB pile while the cap was off ("not short") right after control on the hill. A test of
   `EDEN_PS5_TRANSCODE_PENDING_MIB` alone would not touch that pile. What would: arming the cap regardless of
   the probe, or checking why the probe said "not short" there.
4. **The door count run must be repeated**, as its own queue item with the house save
   `ocarina-owner-after-handplay-2026-11-08` (one item per save; do not mix door and exit runs in one plan).
   One run is enough for counts. Two would also show whether the door load ever gets a non-zero line.

Corrections:
