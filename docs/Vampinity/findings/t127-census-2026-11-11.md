# T127 draw census: what repeats from one frame to the next (11 Nov 2026)

> **Found:** Almost no draw repeats exactly from one frame to the next (0.0-0.5%), so replaying draws from the last frame is worth about +0.0 fps; about half the draws keep their shape.
>
> **So:** Exact replay of draws is not worth building; look for what changes in the other half (most likely a target or texture that alternates between two copies).

Runs read: run1147 (standing at the heavy spot, the overlook at the tunnel mouth with the village and
the water in view) and run1148 (walking loop between the hill and the overlook, through the tunnel).
Source read: `video_core/nx2_draw_census.h` and the rest of `t126/draw-census.reanchored.patch`
(T127 = T126 + 0566, commit ecd79a0). Read-only everywhere; nothing on the PS5 or the queue touched.

## Short answer

- **Almost nothing repeats exactly.** Standing still, only 0.1% of a frame's draws have the same
  bindings as a draw in the frame before; walking, 0.0-0.5%. Replaying whole draws from the last
  frame is worth about 4 draws a frame: **+0.0 fps**. All three draft speed-ups are about smaller things
  than that, and the census weakens two of them.
- **About half the draws keep their "shape"** (same pipeline, same textures, same render targets) from
  one frame to the next: 48% standing, 41-50% walking. Standing and walking give nearly the same share.
  So the other half is not missing because things move. Some piece of the shape changes every frame,
  most likely a target or texture that alternates between two copies. The census cannot say which.
- **Inside one frame, shapes repeat a lot:** 3,690 draws use only about 736 different shapes. So about
  80% of draws could reuse texture and descriptor work done earlier in the same frame. Only 10% sit
  right after a draw with the same shape, and that 10% is all today's "reuse the previous draw" path
  can reach.
- **The piece that changes in every draw is the uniform buffers** (small blocks of per-object data,
  such as where the object sits). Before each draw the game points them at a fresh address: about 11
  constant-buffer address writes and 3.2 binds per draw, only 0.37 of them to the same place. It also
  writes about 7 words (about 30 bytes) of constants inline. This is one small thing per draw, but it
  is the buffer side (about 3 us of the 8.7 us), not something replay can skip.
- **The one design it points to:** reuse resolved textures and descriptors across any draw of the same
  frame, keyed by pipeline + texture handle words. That means a multi-entry texture memo, separated
  from the fast-draw switch, not a frame-to-frame replay. Honest ceiling about +1.5 to +2.5 fps at the
  heavy spot; realistic about half of that.

Thin data: one run per route. See "What a repeat needs" at the end.

## Terms (one line each)

- **Draw**: one "draw this object" command the emulator turns into a GPU draw.
- **Back thread**: the emulator thread that prepares each draw for the GPU (looks up the pipeline,
  textures, buffers); in the heavy view it is the wall.
- **Pipeline**: the compiled shader program plus fixed render settings a draw uses.
- **Shape** (census word): pipeline + the texture views and samplers the draw resolved + render-target
  addresses.
- **Bindings** (census word): shape + every vertex, storage, texture and uniform buffer address and size
  + index-buffer range + draw parameters (first index, count, base vertex, instances, topology).
- **Full**: bindings + a hash of the bytes in every enabled uniform buffer of up to 4 KiB.
- **Uniform buffer (UBO / constant buffer)**: a small block of per-draw data, such as a matrix or a
  colour.
- **Multiset match**: a draw counts as repeated if any not-yet-matched draw in the last frame has the same
  fingerprint. Order is ignored ("same position" checks order).
- **A->B->A**: a register written to a new value and back, so the net change since the last draw is nil.
- **Texture memo**: an existing cache (inside the fast-draw switch) that remembers one pipeline's last
  resolved textures.

## How the census samples, and what its self-check proves

- Every 16th frame starts a pair: a build frame, then the very next frame as the compare frame. Each
  draw of the compare frame is matched against the build frame (multiset, and also by same position).
  Reports every 10 s. At the heavy spot that is 11 pairs (22 frames) per 10 s.
- Register counters run on the same sampled frames. Back-thread counts are per recorded draw. The front
  counts are per draw command it sends, about 16,000 a frame against 3,690 recorded draws (4.35 to
  1). Most likely the draw manager folds repeated instance commands into one host draw, so the back
  also sees 4.35 draw-begin/draw-end writes per recorded draw. **Multiply the front line's per-draw
  figures by about 4.35 to compare with the back.** Then they agree: about 92 writes sent, 43 dropped
  as same-value, 49 reaching the back.
- **Self-check**: once per boot, at the first compare frame, every draw of that frame is looked up in its
  own table. In both runs it ran at 45 s / 35 s on the title screen: "1 of 1". It proves the table insert
  and lookup work. It does not prove anything at 3,700 draws, and it never runs again. "Passing
  throughout" cannot be confirmed. Other consistency checks do pass in play:
  - overflow 0;
  - texture-unknown 0, so every draw's shape includes its real textures, because the fast draw is
    off;
  - indirect 0;
  - draws without a boundary 0;
  - the back-line draw count equals sampled frames x (requests - not executed), for example 22 x
    (4,129 - 435) = 81,268 against 81,283 printed.

Which piece changed (the finest classes the line gives):
- The line has three levels: shape, bindings, bytes. It does **not** split a shape miss into pipeline,
  texture or render target, nor a bindings miss into uniform, vertex or index buffer.
- **Bindings to bindings + bytes:** no extra loss (0.1% to 0.1%). On the few draws whose bindings
  repeat, the uniform contents also repeat. Uniform contents never had a chance to be the reason,
  because the addresses had already changed.
- **Shape to bindings:** 48% to 0.1%. Almost every draw whose pipeline and textures repeat still has a
  different buffer address or draw parameter. Draw parameters are fixed for a still mesh, and the
  constant-buffer address register is rewritten 4.2 times a draw and never left the same. So the
  uniform buffer addresses are the changing piece. This is a strong inference, but the census does not
  separate them from vertex buffers.
- **Shape itself:** 52% miss standing still with a still camera. Inside the frame only 736 different
  shapes exist. Most likely half the draws use a target or texture that alternates between two
  copies frame by frame (double buffering, or a texture made from the last frame's picture). The
  texture cache's view churn is another candidate (5,604 images made, 3,332 deleted in the run). The
  census only compares neighbouring frames, so it cannot tell these apart.

## 3. What it means in plain words

**Best case (standing still) and realistic case (walking) are the same story.**
- Repeated exactly from the last frame: 0.1% (about 4 of 3,690 draws).
- Repeated in pipeline and textures only: 48% standing, about 45% walking.
- Nothing repeats in its buffers.

**Upper bounds for the fps gain.** Frame time is 57.0 ms at 17.53 fps. The back does about 8.7 us of
timed work a draw: about 32 ms a frame at 3,690 draws, inside about 50 ms of back busy time.

| What could be skipped | Draws | Work skipped a draw | ms a frame | fps if nothing else limits |
|---|---|---|---|---|
| Whole-draw replay from last frame (what was measured) | about 4 (0.1%) | 8.7 us | 0.03 | +0.0 |
| Impossible ceiling: all work of every same-shape draw | 1,770 (48%) | 8.7 us | 15.4 | 24.0 (+6.5) |
| Same-shape draws skip pipeline lookup + read handles + fill views + push descriptors (0.31+0.94+0.77+0.33) | 1,770 | 2.35 us | 4.2 | 18.9 (+1.4) |
| Same, but reusing any earlier draw of the same frame (about 80% of draws, from 736 shapes per 3,690) | about 2,950 | 2.35 us | 6.9 | 20.0 (+2.5) |
| Today's previous-draw path (same-shape runs, 10%) | about 375 | 2.35 us | 0.9 | 17.8 (+0.3) |

**The second row is not reachable.** The buffer third of each draw (bind stage buffers 2.0 + update
buffers 0.97 us) has to run anyway, because the uniform addresses change every draw.

**Other limits on the frame:**
- The back's untimed time (about 15-18 ms a frame of register decode and method dispatch);
- the driver submit on its own thread (about 11 ms a frame at heavy);
- GPU time, which is not logged for the heavy view.

The light view runs at 36.5 fps, so nothing else is known to cap the frame above about 27 ms. Each
row is a ceiling and assumes the reuse check costs nothing. A realistic win is half of row 4 or less.

**What changes in the draws that do not repeat.** It is one small thing per draw: the uniform buffer
pointers.
- About 3.2 uniform binds a draw at new addresses, plus about 7 inline constant words.
- The data behind the pointers is about 3 KB a draw (11 MB a frame).
- The census cannot say whether the bytes at the new address match last frame's bytes at the old one.
  Its "full" fingerprint includes the address, so a static object whose matrix was copied to a new
  place still counts as changed.
- A cheaper path could re-point the uniform bindings and keep everything else. But that is exactly the
  part that costs about 3 us today, so "patch in the matrix" is not cheap unless the bind itself is
  made cheaper, for example by binding into one stream buffer with an offset instead of a full bind
  and translate.

## 4. The three drafts

| Draft | Its own bar | Census | Verdict |
|---|---|---|---|
| **reg-net-filter** (drop A->B->A writes inside a register block) | z of at least 5 a draw; "under 3, do not test for speed" | z = 0.97 standing, 0.79-0.95 walking. Its review says the in-block share is lower still | **Weakened.** Retire for speed, with this reason. Keep the patch only if a later design needs it |
| **ubo-rebind-keep** (skip the walk for a same-address uniform rebind) | same binds of at least 3-4 a draw; under 2 only "a free part of a bigger set" | 0.37 a draw standing (1,370 a frame), 0.5-1.55 walking | **Weakened.** The game rebinds to new addresses, not the same one. Free rider only |
| **reg-blocks-live** (pack register writes into blocks) | about 15 direct state entries a draw, 5 CB words a draw | about 49.9 direct entries a draw. About 28 are executable (draw, binds, reports) and about 7 are CB words. That leaves roughly 14-15 state-like direct entries (mostly CB address), plus 7.4 CB words in mode 2 | **Neutral to mildly supported.** It does not depend on repetition. At its bar; its own counter line decides; expected +0.15-0.45 fps |

**The one design for the next speed build: a frame-wide texture/descriptor reuse cache.**
- **What it is:** the existing fast-draw texture memo, made independent of EDEN_UP_FAST_DRAW and with
  several entries per pipeline instead of one. It is keyed by the pipeline plus the texture handle
  words read from the constant buffers. On a hit, the draw skips read handles and fill image views,
  and the descriptor push it can.
- **What it does not do:** it does not skip the buffer work. Uniform buffers keep going through the full
  path.
- **Why the census supports it:** 736 shapes for 3,690 draws, so about 80% of draws repeat a shape
  already seen this frame, against 10% back to back. This holds standing and walking alike.
- **Ship with:** a VERIFY mode (resolve in full and compare, as the memo's verify already does) and a
  10 s hit-rate line.
- **Ceiling:** +2.5 fps at the heavy spot, realistic about +1.

## What the census cannot see

1. It compares only neighbouring frames, never a frame against the one two back. A target that
   alternates between two copies looks like a change every frame.
2. It does not split the shape (pipeline / textures / targets) or the bindings (uniform / vertex /
   index / storage / draw parameters). The "uniform addresses" conclusion is an inference from the
   register counts.
3. It has no "same bytes at a new address" class. Whether a static object's constants are byte-equal
   to last frame's is unknown.
4. The shape is taken after the textures were resolved, by view id. A cache keyed before resolution
   (raw handle words) might repeat more or less often. Number of pipelines a frame: not logged.
5. Uniform buffers over 4 KiB (about 0.9 a draw) are matched by address and size only.
6. The self-check ran once, on a 1-draw title frame.
7. Two of every 16 frames are sampled, so short events between samples are missed. 2,500+ compare
   draws per window make the shares themselves solid.
8. Its cost was not measured on/off: the plan was A/A.

## What a repeat needs to confirm

- **Standing:** one more run at the overlook on another boot, plus one at a second heavy view (the
  village square). Check that the 48% / 0.1% / 736-shapes picture holds within a couple of points.
- **Walking:** one more loop run, ideally a route that stays in open views (the field) and not only
  the tunnel.
- **Cost:** a live plan A = census off, B = census on, 3 rounds, at the overlook. Expect about -0.2
  fps.
- **Census v2** (diagnostic, before the speed build). Add these:
  - a frame N against N-2 comparison;
  - a bytes-only uniform fingerprint without addresses;
  - shape split into pipeline / textures / targets;
  - a raw-handle key with its within-frame repeat share;
  - pipelines a frame;
  - the self-check on the first in-play pair, repeated at every report.
- **Choosing the build:** if N-2 brings the shape share to about 90%, a two-slot (even/odd frame)
  memo is the cheapest version of the design above. If the raw-handle key repeats as often as the
  shape within the frame, the frame-wide memo is confirmed.

## Check (second time)

I re-read every "Draw census" line in both eden_log.txt files with my own parser, re-read
`nx2_draw_census.h` (t126/chain5/full, identical to t126/stack) and the CensusDraw / binds-hook parts of
`draw-census.reanchored.patch`, and looked at frames f0040 (run1147) and f0033 (run1148).

**What holds.**
- Both runs are valid. f0040 shows Link standing at the overlook with the village and water in view;
  f0033 shows him running up the hill. run1148 has three `steer_met 25/25` lines (111, 145, 178 s).
  Standing in-play lines (135-275 s, 15 windows): 3,678-3,752 draws a frame, same shape 47.8-48.2%,
  same bindings 0.1%, same bindings + uniform bytes 0.1%, same position 0.0%, shapes 734-738,
  runs of 2+ 10.0-10.2%. Walking (105-215 s, 12 windows): 879-2,651 draws (mean 1,394), shape
  40.5-50.1% (mean 45.5%), bindings 0.0-0.5%. All match the report. Boot/menu lines (1-45 draws,
  up to 95 s) are rightly dropped; the 95 s walking window (overflow 26) too.
- The shares mean what the report says: each is a share of the compare frame's draws that found an
  unused twin in the build frame (multiset), not a share of pairs. "Same shape" is pipeline pointer +
  resolved view/sampler ids + render-target and depth addresses, not an identical draw. Bindings use
  guest addresses (device_addr), so a stream-buffer offset cannot fake the 0.1%.
- fps: six live phases average 17.53 (17.45-17.60). Census cost 6.0 ms x 2/16 = 0.75 ms a frame, about
  -0.23 fps. Self-check: once only (`self_checked` never resets), "1 of 1" on a 1-draw title frame.
- Whole-draw replay worth +0.0 fps; reg-net-filter and ubo-rebind-keep weakened. Arithmetic of the
  bound table rows is right as written (57.0 ms minus 4.2 / 6.9 / 15.4 / 0.9 ms).

**Corrections.**
1. **The fps ceiling is too high.** The design is keyed by pipeline + texture handle words, so a hit
   still pays the pipeline lookup (0.31 us) and at least part of "read handles" (0.94 us), which is
   what reads those words. Skippable per hit is at most 2.04 us, and only about 1.10 us (fill views +
   push descriptors) if reading the handles stays. 2,954 hits x 2.04 us = 6.0 ms gives 19.6 fps
   (**+2.1**, not +2.5); x 1.10 us = 3.25 ms gives 18.6 fps (**+1.1**). Realistic is then about
   +0.5 to +1. Also unverified: if uniform buffers sit in the same pushed descriptor set as the
   textures, the push (0.33) cannot be skipped while uniform addresses change every draw.
2. **"80% holds standing and walking alike" is wrong.** Within-frame reuse (1 - shapes / draws) is
   80.0-80.3% standing but 56-76% walking (draw-weighted 67%). Fewer draws a frame means fewer
   repeats. Use about 2/3 for the walking case.
3. **Per-draw figures in the "runs" line are per request, not per recorded draw.** The source divides
   them by ProcessDraw requests (about 4,125 a frame, including 435 not executed), not by the 3,690
   recorded draws. Per recorded draw: binds 3.58 (the back class line prints exactly that), same
   binds about 0.41, CB address 12.56, A->B->A z about 1.08. No verdict changes.
4. **"address_low is never left the same" is true only on the back.** The front dropped 0.63 of 1.60
   writes of 0x8e2 per draw trigger as same-value (about 39%), so the game does re-write the same
   address; the front filter hides it. The direct evidence for "uniform binds go to new places" is
   the binds-same counter (0.37 per request), and that stands.
5. **"Runs of 2+" is narrower than "back-to-back same shape".** A run also needs no state-register
   change in between, so 10.2% is a floor for adjacent same-shape draws, not the share itself.
6. **reg-blocks-live "14-15 state-like direct entries" is an estimate the line cannot give.** Entries
   are ring entries, not writes, and the class split is per write: state 5.09 + CB address 12.56 =
   17.7 writes a draw, part of which arrive in sinks (4.55 entries a draw). The figure lies somewhere
   in 13-18. "Neutral, at its bar" still holds; its own counter line decides.
7. Small: plan.json sits in the batch folder (auto-20261111-161810-...), not in the run folder; the
   run folder has live.json with the same A/A phases.

**Corrected verdict.** Runs valid, one per route. Replay from the last frame: +0.0 fps. About half of
draws keep their shape frame to frame; uniform binds go to new addresses (0.37 of 3.2 per request
same). Within a frame, 80% of draws standing and about 2/3 walking repeat an earlier shape. A
frame-wide texture/descriptor memo is still the one design the census points to, but its honest
ceiling at the heavy spot is about **+1.1 to +2.1 fps, realistic +0.5 to +1**, and less when walking.
A repeat should also log the memo's key cost (read handles split from TIC/TSC decode) before building.
