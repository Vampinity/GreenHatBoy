## Words used (one line each)

- *largest free block*: the biggest single piece of free GPU memory. The morning crash came at 2 MiB.
- *free pool*: all free GPU memory, from the driver's own line (`RADV_PS5_MEMORY available_mib`). Here it nearly
  always equals the largest free block, because the free memory is in one piece.
- *census*: the `EDEN_MEM_CENSUS` line, written every 2 s while the largest free block is under 768 MiB. That was
  true from the house onward in every run, so the series has no gaps. `largest=` is the value now. `low=` is the
  lowest since the last line, so it catches dips shorter than 2 s.
- *images held*: GPU image bytes alive (`images=` MiB in the census).
- *window*: after a burst of 100+ new images, the clean-up deletes images that have not been used for 40 frames.
- *veto*: with the budget on, a burst that mostly brings back images deleted here in the last 600 frames opens no
  window.
- *refusal fallback*: an image went over the memory budget while a window was counting. That window then runs the
  old, unbudgeted way.
- *budget-capped pass*: a clean-up pass that the budget stopped early.
- *re-made*: an image that was deleted and then built again within 600 frames (about 25 s). Only budget runs count this.
- *over-budget image*: the driver allocates an image even though it is over the memory budget (a warning, not a failure).
- *worst frame*: the longest single frame in a 5 s fps line (`nx2:vi2 5 s`).

## 3. Answers

### Does the budget cost free memory at the door load?

No sign of it here.
- **Door load** (fly-over and greeting), lowest largest free block: on 60 / 128 / 122 MiB against off
  109 / 85 / 92. Means 103 against 95. The spread inside each arm (68 and 24 MiB) is larger than the 8 MiB
  difference.
- **Change to the standing view**, the deepest point of the route in every run: on 17 / 21 / 17 (low 4 / 16 / 17)
  against off 10 / 8 / 18 (low 1 / 8 / 13). The **lowest of the batch, 1 MiB, is c1, an off run**, at 110.0 s with
  2,415 MiB of images held. Two off runs went lower than any budget run. The driver's free pool bottoms at
  16-37 MiB in all six.
- Images held at those lows are the same in both arms (2,321-2,510 MiB). The dip is the game loading the standing
  view on top of the greeting's images, in every run.
- The first pair's "2 MiB low in the budget run" does not hold up as a budget effect. That dip happens in every
  run, and in this batch an off run went deepest.

### Does it cost free memory during the village stay?

No.
- Median largest free block over the same 120 s of standing: on **63 / 76 / 154** MiB, off **98 / 134 / 86**.
  Means 98 against 106. The 8 MiB difference is small next to the spread inside each arm (91 MiB on, 48 off).
  The budget arm has both the lowest (b1, 63) and the highest (b3, 154) value of the batch.
- Images held while standing: 1,755-1,770 MiB in all six. The headroom is set by how the free memory happens to be
  cut up in the first seconds after the change, not by what the clean-up kept.
- The budget's own lines are silent while standing (all 10 s lines 0 in the stay, no vetoes there), so it is not
  doing anything there that could cost memory.
- All six stay values (58-154 MiB) are lower than in the first pair (165-269). Both arms moved, so the cause is
  not the budget. These runs stand for 183 s with live phases; the first pair stood for 20 s.

### Run order (drift)

- Village-stay median in run order: b1 63, c1 98, b2 76, c2 134, b3 154, c3 86. There is no steady drift; it goes up
  over the first five runs and drops at the sixth.
- **b1 is the odd one out** in several ways. It was the first run of the batch, needed the save put back, and booted
  9 s slower. It also had the lowest stay block (63), deleted 2,243 MiB, and was the only budget run whose house
  window closed "budgeted". In the first pair, the budget run (run1127) was also first in its batch. So "first run
  after a fresh start" is a likelier explanation for the first pair's low headroom than the budget. This is an
  inference from two batches; it is not tested.

### What the budget did change

- **The house window closes early.** In b1-b3 the house window closed at frames 3250-3273, before the door
  (b1 "budgeted", b2/b3 "opened unbudgeted, budget left 0"). In all three off runs the house window was still open
  through the door press (closed at 3561-4089), so the door load fell inside it. With the budget on, the door press
  opens a window of its own (burst 2, 285-431 new images). The over-budget images then send that window back to the
  old path (2-3 refusal fallbacks per run).
- **Deleted bytes differ, but memory does not.** b2/b3 deleted 615/689 MiB against off 1,169-1,918, and b1 deleted
  2,243. Images held and free memory end up the same either way.
- **Re-made**: 254-664 MiB of images were rebuilt within 600 frames in the budget runs. The off runs have no counter,
  so it cannot be compared. Whole-run collector uploads: on 26,724 / 25,023 / 27,202 MiB, off 24,632 / 25,161 /
  25,141. Two of the three budget runs uploaded about 1.5-2 GiB more. This is a weak sign of extra rebuilding, inside
  the noise for b2.
- **Never limited**: 0 budget-capped passes in all three runs. On this route the budget never actually held a
  deletion back. Each window it opened either finished with budget left or fell back to the old path.

### Two small differences that go one way 3 of 3 times

With three runs per arm, the chance that all three on runs land on the same side of all three off runs is 1 in 20
for each measure.
1. **Standing fps**: on 22.24 / 22.27 / 22.12, off 22.37 / 22.42 / 22.38 (5 s lines). live.json: on 22.05-22.27,
   off 22.33-22.37. That is 0.1-0.3 fps lower, under 1.5%, which nobody can feel. The budget is idle while standing,
   so there is no known reason for it. The t126b exit runs pointed the same way (both budget runs lowest, by
   0.3-0.8 fps). It could be chance, or a cost that shows up elsewhere, for example in the uploads.
2. **Worst frame at the door press**: on 268 / 216 / 246 ms, off 190 / 198 / 211. That is about 45 ms more on a
   one-off hitch, roughly one extra frame at 22 fps. It fits the budget runs opening a new window at the door
   instead of carrying on the open house window. The fly-over and the change hitches show no difference
   (312-375 against 330-357 ms).

## 4. What this test could and could not see

Could see:
- Free memory every 2 s from the house to the end, plus `low=` for shorter dips.
- The driver's free pool every few seconds.
- Every clean-up window, veto and fallback.
- Over-budget and refused allocations.
- 5 s fps lines and the worst frame in each.
- Whether each run reached the standing view, from frames every 5 s.

Could not see:
- Dips shorter than one frame that `low=` misses.
- Visual glitches. The frames only check the route.
- What the off runs re-made, since they have no counter.
- The pause menu, where the budget's gain is.
- The door walked out and back within 600 frames.
- A long play session.
- Any effect of starting first in a batch, which was not controlled.

Each arm is three runs on one route.

## 5. Verdict

- **Safe to offer as an optional play setting: yes.** Across six runs there were no crashes, no refused images or
  buffers, no driver out-of-memory lines and no lost textures. The free memory at the door load and in the village
  is the same as without it, within the run-to-run spread. The deepest dip of the batch was an off run. The first
  pair's low headroom was chance, probably helped by being the first run of its batch. The gain stays the pause
  menu (`t126-results-2026-11-11.md`). The one-line risk note can now say "same memory as off on the door load".
- **For a later default, two things argue for more checking first, not against it outright:**
  1. Standing fps was 0.1-0.3 lower in all three budget runs here, and in both budget exit runs before. It is tiny,
     but it keeps showing up and there is no known cause.
  2. The door press is about 45 ms worse on its worst frame, because the budget closes the house window early and
     opens a new one at the door. That window then falls back to the old path anyway. Two of the three budget runs
     also uploaded 1.5-2 GiB more over the run.

  Neither is a memory risk. The fps check needs a longer standing or play run, on/off alternated, with the first
  run of the batch thrown away. The door-hitch check needs the door walked out and back within 600 frames, as
  t126b already proposed.

**Corrections.**
1. *The first pair's "165 against 229-269" was not the village stay.* t126b measured it at census 78-107 s. In the
   first pair the change to the standing view is at 108.5-108.7 s (area census), so 78-107 s is the fly-over and the
   greeting, i.e. this report's "door load", not its "village stay". Re-read from the first pair's own logs, the real
   standing stay (112 s to the end) has median 80 (run1127 on), 97 (run1128 off) and 86 MiB (run1136 check), right
   inside this batch's 58-154. So the report's line "All six stay values are lower than in the first pair (165-269).
   Both arms moved ... these runs stand for 183 s with live phases; the first pair stood for 20 s" is wrong twice: the
   values did not move, and the first pair ran the same script with the same live phases (env differs from c1 only by
   the budget line). It also contradicts the report's own finding that the stay value is set in the first 5 s.
2. *So the open question belongs to the door-load window, and there the answer depends on the window.* Median
   largest free block in the fly-over and greeting:
   - t126b's own window, 78-107 s: on 265 / 208 / 154, off 257 / 205 / 412. No separation (b1 and b2 sit above c1
     and c2).
   - The report's door-load window (press to T2-1): on 220 / 208 / 154, off 249 / 230 / 412. All three on below all
     three off. This row is in the report's table but not discussed in the answers.
   The free block there is a step curve that holds one value for 10-20 s, so the median flips with a few seconds of
   window. Read with the first pair (on 182, off 318, check 236 in 78-107 s), the budget runs are often lower in the
   fly-over, but not in every window, and the gap is smaller than c3 alone (412, raised by its extra window). Verdict

   (60-128 MiB in the fly-over, 1-17 MiB at the change) do not differ by arm.
3. *"1 in 20 by chance each" overstates.* 1 in 20 is the one-sided chance for a direction named in advance. The fps
   direction was named in advance (t126b), so 1 in 20 fits there. The door-hitch direction was not: two-sided it is
   1 in 10. And the report compares about 15 measures across the arms; one or two full 3-of-3 separations are expected
   by chance alone among that many (the door-load median in correction 2 is a third one).
4. *The door-hitch cause is a guess, stated as fact.* The 5 s line only gives the worst frame, not when it fell. In
   that 5 s line every run builds the same two slow mesh pipelines (63-70 ms each, 131-150 ms in all), and the
   over-budget image plus "Out of device memory: keeping 1536 MiB more free" appear in c1 too. The budget runs do open
   their door window inside that line (burst 2 at 64.3 s), so the report's explanation fits, but nothing in the logs
   ties the long frame to it. Say "fits", not "because".
5. *"The deepest dip of the batch was an off run" is true but weak.* c1's 1 MiB is one `low=` reading; c2 8, c3 13 and
   b1 4 are all within a few MiB of each other. The change dip is the same in both arms; "an off run went lowest" adds
   nothing beyond that.

**Run order.** In run order the stay medians go 63, 98, 76, 134, 154, 86: no steady drift. Door-load medians 220,
