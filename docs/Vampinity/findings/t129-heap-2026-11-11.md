## Answer first

**No, this batch did not test the fix.** The test aid refused **zero** heap growths in all five runs that had it.
- The heap hardly grows after 120 s on this route: **0 to 2 growths per run** after the 120 s mark. The aid
  refuses only the **8th** growth after 120 s, so it never fired.
- No request reached the "about to be refused" point. So the steal never ran, and the control had nothing
  that could kill it.
- What the batch did give: **six clean no-fault runs with the switch present**. Four had the steal on
  (modes 1, 2, 3, 3) and one had s3. That counts as a cost check, and there is no visible cost.
- Even `NO_GROW=1` (every growth) would not put the crash-size requests at the refusal point on this route.
  After about 30 s, those requests never make the heap grow. What still grows later is arena blocks (the
  steal skips those on purpose) and 8 to 32 MiB requests (too big for the steal). The smallest reliable
  fix is a small change to the aid, not to the env. See section 6.

Terms used below:
- **heap**: the app's own memory for ordinary C/C++ allocations.
- **pool**: the console's free memory that the heap, graphics and the game all share.
- **growth**: the heap taking another 32 MiB piece from the pool.
- **refusal point**: where `eden_heap_main` found no room and could not grow. The steal hooks in there.
- **arena**: a 2 MiB private heap a thread uses without locking. An **idle arena** is one no thread is on now.
- **spill**: a small request the thread's arena could not take, sent on to the shared heap spaces.

## 2. What NO_GROW actually did

**Where it acts** (`heap_arenas.inc:843-854`, called at `:934`):
- It runs inside `eden_heap_grow`, just before the 32 MiB piece is committed.
- It counts growth attempts only after `after_s` (process time). Every `every`-th attempt is refused as
  "the console has no memory for a new piece" (reason 2).
- It counts nothing else. A request served from room the heap already has never reaches it.

**Growths after 120 s.** The heap's 20 s line `EDEN_HEAP_GROWTH ... grew:` gives MiB by request kind. One
arena or one piece under 8 MiB is one growth; a 24 to 31 MiB request takes one or two pieces. The
`RADV_PS5_MEMORY t_s` clock runs about 5 to 10 s behind process time, so the 120 s mark is near RADV t≈110-115.

| run | heap at RADV ~101 s (arena / under8M / under32M MiB) | at the end | growths after ~101 s |
|---|---|---|---|
| 1196 s3 | 384 / 96 / 736 | 416 / 96 / 736 | 1 (arena, by t=121) |
| 1197 g1 | 288 / 64 / 800 | 352 / 64 / 800 | 2 (arena by t=121, arena at t=147-165) |
| 1198 g3 | 320 / 96 / 736 | same | **0** |
| 1199 g0 | 384 / 128 / 672 | 384 / 128 / 704 | 1 (one large piece, by t=121) |
| 1200 g3b | 352 / 96 / 736 | 352 / 96 / 768 | 1 (one large piece, by t=121) |
| 1201 g2 | 256 / 160 / 768 | 256 / 192 / 768 | 1 (under 8 MiB, t=147-166) |

- Counted from RADV 101, which is earlier than 120 s process time, the most is **2 growth attempts**. The aid
  needs **8**, so `eden_heap_no_grow_refused` stayed 0 in every run.
- That is confirmed in g1, g2, g3 and g3b. The steal's 10 s line includes "test refusals" in its "moved?"
  sum (`performance.cpp:921-924`, `v[24]`), and no such line ever printed. So the count was 0 there.
- Nearly all growth happens in the first ~100 s (boot, then the area load around 60 to 100 s). By 120 s the
  heap holds 1368 to 1400 MiB, and 56 to 158 MiB of it is whole free 2 MiB pages, so later requests fit in
  room the heap already has.

**What a refused growth would have done** (it did not happen here, but this is what the test depends on):
- `eden_heap_grow` returns 0. Then `eden_heap_main` (`:1101-1105`) hands the request to `eden_heap_steal`
  when the steal is on, or returns NULL when it is off. This **is** the refusal point; there is no hidden
  retry inside eden_heap_main.
- After that, the outcome depends on the kind of request:
  - **Arena block** (a thread asking for a new 2 MiB arena): the steal returns NULL at once, and on purpose
    counts nothing (`:2200-2201`). The thread then sets `retry=256` and spills (`:1418-1424`, `:1435-1438`).
    The spill calls eden_heap_main again. That is a new growth attempt (number n+1), and it is **not** refused
    while every>1, so the request is served. A refused arena block is healed at once and leaves no trace in
    the steal counters.
  - **8 to 32 MiB request**: the steal counts "too big" (`:2205`, cap ~1.94 MiB) and returns NULL. That
    request fails in every arm.
  - **64 KiB to 1.9 MiB request** (the crash size): served or missed by the steal. In the off arm it is NULL.
    Then a pipeline builder asks again every 2 ms for up to 2 s (`EDEN_UP_HEAP_WAIT_MS=2000`, `:2588-2612`),
    and its next try makes a new growth attempt that is not refused, so it would be healed in 2 ms. Any other
    thread gets NULL, as in the real crashes.
- On this route, after ~30 s, crash-size requests **never** made the heap grow. under1M stays at 32 to 96 MiB
  and under256K at 0 from the t=29 line onward. So a refusal could only have hit arena blocks or big requests.

## 3. EDEN_UP_HEAP_STEAL counter lines

- **There are none**, in any run. Each steal run shows only its start line.
- The code explains why (`performance.cpp:905-944`, called every 100 ms from RefreshFreeMemory when the mode
  is not 0):
  - The first call only starts the clock.
  - After that, a line prints at most every 10 s, and only when the sum of triggers, scans, served, misses,
    lock waits, test refusals or the v2 counters has changed.
  - A trigger needs a refused growth (`eden_heap_main:1104`). In mode 3 the "before a growth" path needs
    `eden_heap_steal_pool_no_us`, which is set only by a refused growth (`:974-976`).
  - With no refusal, every counter stays 0 and the line never prints.
- So triggers, scans, served by kind, would-have-served, misses and lock waits are all 0 in all four steal runs.

## 6. Verdict and the next test

**Verdict: no.** The fix was not exercised. This batch counts as a cost check only (section 5).

**Why the planned aid cannot reach the refusal point on this route, and where in the code:**
1. `eden_heap_test_no_grow` (`heap_arenas.inc:843-854`, hooked at `:934`) acts only on heap **growth**. On this
   route growth almost stops after ~100 s (0 to 2 attempts after 120 s), and after ~30 s crash-size requests
   never grow the heap at all.
2. What does still grow is arena blocks, which the steal skips on purpose and which heal on the next attempt
   through the spill, and 8 to 32 MiB requests, which are too big for the steal.
3. So `NO_GROW=1,60` (every growth) would mostly refuse arena blocks and big requests. Those big refusals hit
   every arm alike. A crash-size refusal would only come once the existing room fills up. That shortfall is
   about 200 MiB, more than the idle arenas hold here (0 to 28 MiB of empty idle arenas in today's runs). So
   the steal arms would probably die too, and the test would not separate the arms.
4. `EDEN_TEST_POOL_HOG_MIB` has the same weakness. The heap asks the pool 0 to 2 times after 120 s, while
   graphics asks all the time, so graphics hits the shortage first. Today's lows: census 16 to 72 MiB, RADV
   64 to 240 MiB. The tester env drove the pool to 20 to 26 MiB on this route with 0 heap failures
   (runs 1161, 1176). If used anyway, 96 MiB is the number (the highest census low, 72, plus one 32 MiB piece
   minus margin). Expect the graphics side to fail first, and read where it ended.

**Smallest change that works: a "brink" aid aimed at crash-size requests** (rebuild needed, about 15 lines in
heap_arenas.inc). In `eden_heap_main`, right after `bytes` is computed (`:1070`), before the spaces are asked:

```c
/* EDEN_TEST_HEAP_BRINK=<every>,<after_s>: from after_s on, every n-th request of 64 KiB..EDEN_HEAP_STEAL_MAX
 * (never an arena's own block) is treated as "no room in the spaces and the pool refused": it goes
 * straight to the refusal point. Mode 3 also gets its 1 s "pool said no" window, as a real refusal. */
if (eden_heap_test_brink(kind, a, b, bytes)) {
  if (atomic_load_explicit(&eden_heap_steal_mode, memory_order_relaxed) >= 3)
    atomic_store_explicit(&eden_heap_steal_pool_no_us, (unsigned long long)sceKernelGetProcessTime() | 1u,
                          memory_order_relaxed);
  return atomic_load_explicit(&eden_heap_steal_mode, memory_order_relaxed) != 0
             ? eden_heap_steal(kind, a, b, bytes, 0) : NULL;
}
```

- `eden_heap_test_brink` is `eden_heap_test_no_grow` with a size filter (skip below 64 KiB, above
  `EDEN_HEAP_STEAL_MAX`, and the arena block `a==EDEN_HEAP_ARENA_SIZE && b==EDEN_HEAP_ARENA_PAYLOAD`).
  `EDEN_HEAP_STEAL_MAX` is defined at `:2003`, so either move the define up or use `((size_t)2 << 20) - (64 << 10)`.
- A spill of 64 to 256 KiB passes through eden_heap_main too, so the tester's 160 KiB GPU-thread case is covered.
- **Reporting, two lines:**
  - Add `seen` and `refused` for the aid to the 20 s heap summary (WriteMemorySummary), printed whatever the
    steal mode is. Then the control shows its count too.
  - Optionally print the first refusal to stderr from the 100 ms reporter, not from the allocator, because
    no stdio is allowed there.

**Rate.** Requests of 256 KiB to 2 MiB ran at about 70 per second after 120 s, steady to the end (~5,700 between
RADV 121 and 202). `EDEN_TEST_HEAP_BRINK=50,120` therefore gives about 1.4 refusals per second, roughly 120
in the ~85 s left, plus the 64 to 256 KiB spills.

`EDEN_UP_HEAP_STEAL_TABLE`). Order: count first, so the aid is proven before the control; then off, 3, 3, off, 2.

  the builders' arenas go idle, not to a harsher aid.

**Env-only fallback on T129 now (no rebuild):** `EDEN_TEST_HEAP_NO_GROW=1,90`, the same four arms.
- From process 90 s this refuses every growth, which covers the second half of the area load.
- Expected:
  - Arena refusals are healed by spill but leave no steal count.
  - 1 to 2 big requests per run fail in **every** arm. Today's 38 MiB `EDEN_HEAP_FAILURE` in runs 1162 and
    1177 was survived, so this need not crash.
  - Crash-size triggers come only if the existing room fills up.
- It may test the steal a little, and it may crash every arm alike. I would not spend PS5 time on it ahead of
  the brink build.

**Can any of this hang the GPU?**
- Not through the heap code. The steal waits for its lock at most 5 ms, then gives up. It never waits under
  the growth lock and never allocates under its own lock (NOTES section 4, v2). The builders' wait is capped
  at 2 s and runs on background threads.
- The one theoretical route is a NULL handed to the driver's submit thread: if it swallowed the failure and
  never signalled a fence (the "work is done" marker a frame waits for), the frame would wait forever.
  `EDEN_NX2_HANG_WATCH=1` is set in the base env.
- To rule it out completely, the brink filter can skip the submit and GPU threads by name, as
  `eden_heap_may_wait` does for builders. But the tester's real failure was on the GPU thread, so keep that
  as a second step, not the first.
- The pool hog is the riskier one. It makes graphics allocations fail, which is outside the heap code, and
  NOTES section 6 B2 already says it can end a run in the driver.
