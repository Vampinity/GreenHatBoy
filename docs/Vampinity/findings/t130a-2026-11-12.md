# T130 night batches A, B, C: independent check (12 Nov 2026)

> **Found:** The night batches could not show whether the heap steal (EDEN_UP_HEAP_STEAL) works: it was asked but served no counted request, and the fix runs crashed like the controls.
>
> **So:** The heap steal needs a counter line and a test that really hits its case before any verdict.

Checked the first report against the run folders, the T130 source
(`t130-wt/headless/heap_arenas.inc`, `main.cpp`, `performance.cpp`;
`t130/stack/src/video_core/renderer_vulkan/vk_pipeline_cache.cpp`, `shader_recompiler/object_pool.h`)
and the symbols (`llvm-pie.elf`, code size 0x2c5c750 matches the crash reports). Nothing on the console was touched.

## Verdict on the heap steal (EDEN_UP_HEAP_STEAL)

**The test could not show it.** Not "works", not "does not work".

- Read: the steal was switched on in 4 of 6 runs (start lines for mode 1, 3, 3, 2). There is no steal counter line in
  any run. The fix runs crashed the same way as the controls, at the same place and the same moment.
- Read from the source: in modes 2 and 3 every test refusal goes to the steal (`eden_heap_starve_refuse`). The first
  refused request (402440 B, 0.4 MiB) was under the steal's limit (2 MiB - 64 KiB). So the steal was asked, and it
  did not serve that first request in any of the 3 fix runs. Why it missed is not in the logs.
- Inferred, 2 of 2 runs: in both mode-3 runs the second failure was a different request (1207304 B, 1.2 MiB). In the
  off, count and mode-2 runs it was 402440 again. The `count=` number counts every failed heap request in the whole
  run, so in mode 3 the request that killed the other runs did not fail. The likely reason is that the steal served
  it. This is the only sign of the steal doing anything, and it is not read from a counter.
- Why there are no counters: the 10 s steal line is only printed from the GPU thread's memory check. The refusals
  came a few milliseconds before the crash, and the crash was on that same thread.

Why the test cannot tell "broken" from "nothing to take":
1. The steal only looks in arenas that no thread is on. An arena is one thread's own 2 MiB block of heap. On this
   route the heap had only 6 to 12 MiB of empty arenas of *any* kind at the last 20 s line, and most of them were
   probably arenas that threads were still on. The real crash it was made for had 116 empty arenas (MAP.md).
2. The steal's own 5 ms "just missed" memory: after a search finds nothing, every request of **that size or larger**
   gets a no for 5 ms, with no new search (`eden_heap_steal_cached`: bytes >= last miss). The first read had this
   backwards ("or less"). In all six crash copies, eden_log stops 4-5 ms after the dropped pipeline, so the second
   refusal very likely came inside that window. In mode 2 the killing request was then most likely refused from the
   cache, without a search (inferred: the failure lines have no timestamp).
3. The aid refuses up to 50 requests in a row. Once a request is refused, a second refusal a few milliseconds later
   is almost sure to fail too (point 2).

Point 2 is not only a problem with the test: a real burst of refusals would hit it too. A miss on one request makes
any equal or larger request in the next 5 ms fail for sure.

**Crash site (symbolised, same in all six):** eboot+0xb8655 = our terminate handler, then std::__terminate,

thread's stack. EDEN_UP_HEAP_HOLDERS=1 would catch it (object_pool.h:71-80), but it was off.

**What happened, read:** (1) The 3rd large request inside a run-time pipeline build was refused by the aid. Then

(2) Within about 5 ms, the next refused request was the pool merge above: it is not inside the try block, so the
app

**Corrections to the first read on C:**
- The crash came **while the save was loading, before gameplay** (the hearts WAIT, script line 44, never passed; the
  card says "out of memory, while loading"). It was not "8 s into the first walk". Line 41 at 52.9 s is on the
  script's clock (guest start), not the app's.
- With STARVE_GPU=1 the aid refuses **only requests made inside a run-time pipeline build** (`wait_scope`), not "work
  outside the pipeline build". The killer was inside the build but outside its catch.
- `count=` in EDEN_HEAP_FAILURE is the run's total of failed heap requests (`ps5_heap_failures`, every malloc and
  calloc, C code included). So exactly 2 requests failed in each run. A NULL returned quietly to C code would have
  raised the count, so no such refusal happened. The first read said they "would leave no trace"; they would.
- For a test refusal, `reason=0` is an old value: the last growth reason from any thread. It says nothing about the
  refused request. "Plenty of memory" is still true from the largest free block (3447-3549 MiB) and RADV
  available (~5.7 GiB).
- "idle arenas" in EDEN_HEAP_PAGES = empty arenas of any kind, threads on them or not (the first read had this right).
- Every aid count line says 0. The last one is printed before the refusals (every 20 s). Read.

## Is the starve test fair?

Partly.
- Fair: it refuses inside run-time pipeline builds on the GPU thread, as in the 10 Nov 22:07 crash. It found a real
  weak spot: a refusal during the shader-pool merge (vk_pipeline_cache.cpp:3164) always ends the session. That spot
  matters for the alpha whatever happens with the steal.
- Not fair to the steal: it refuses while the heap has plenty of room, on a route where almost no arena is free of
  threads. It refuses back to back, so the steal's 5 ms miss memory makes the 2nd refusal a sure fail. And the steal
  cannot report before the crash. No steal could pass this test unless arenas that no thread is on happened to
  have room at that moment.

## Consequence for the house-door crash

EDEN_UP_HEAP_STEAL=3 is still **untested**, not disproved, after T129 and T130. Do not drop it and do not ship it as
proven. Two open points:
- At the house door one request was refused (the file-service thread asked for under 1 MiB while ~0.9 GiB sat free
  in other threads' arenas). That is a single refusal, so the 5 ms miss memory would not get in the way. Whether
  the steal can reach that room depends on how much of it was in arenas that no thread is on.
- The pool-merge spot is a separate crash path that the steal does not fix.

## Next tests

1. Build change, no PS5 time: when EDEN_HEAP_FAILURE prints, print the steal counters and the aid counts on the
   same line, plus the time. Also one line per steal miss with its reason (none found / lock busy / cached / too big).

   cheap candidate for the alpha.

   memory when another thread frees into an arena, or letting the same thread try again once.

   none, the steal cannot fix it by design.
