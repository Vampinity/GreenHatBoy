# T128 door walk: does read sync fix the too-bright second? (11 Nov 2026)

> **Found:** EDEN_UP_AHEAD_READ_SYNC=1 removed the too-bright second at the greeting cut (0 of 4 runs against 3 of 3 controls), but it costs about 20% fps after the door.
>
> **So:** The cause is confirmed (a game read of GPU-written data while running a frame ahead); read sync is not shippable as it is, a cheaper form that syncs far less is needed.

Batches: `auto-20261111-221819-batch-t128-door-1` (c f c f), `auto-20261111-222942-batch-t128-door-2` (c f + check-mode run v1),
extra pair `auto-20261111-215019-batch-t128-door-1` (run1205 control finished; run1206 read sync lost the network, logs in
`crash-2026-11-11-2212/`). Extra runs are marked "extra" everywhere and are never needed for a verdict.
Build T128 (daba930, 01.219.028). Door walk: Continue, house, door, village, fly-over with the area card, greeting cut, stand.
Every run: fast (`EDEN_NX2_FRAMES_AHEAD=1`), usage tracker, guard 3. All boots were cold (guest started at 18 s).

Words used:
- **read sync**: `EDEN_UP_AHEAD_READ_SYNC=1`. When the game reads a number the GPU wrote, it first waits for the frame that number belongs to.
- **check mode**: `EDEN_UP_AHEAD_READ_SYNC_VERIFY=1`. Copies the bytes before the wait and after it, and counts the reads where they differ.
- **fence**: the GPU's "this frame is done" marker.
- **escape**: a wait that stops after 2 ms because a GPU channel is waiting on the CPU. The read then goes ahead without the frame being done.
- **greeting cut**: the fade to black about 20-21 s after the door, then the cut to the greeting scene at the house. Earlier notes call it "the cut".

## Answer first

- **The too-bright second is gone with read sync.** The greeting cut was too bright in **3 of 3 control runs** and **0 of 4 read-sync runs** (3 plain runs plus the check-mode run). The extra pair agrees: control too bright, read sync clean. All runs together: 4 of 4 against 0 of 5.
  - The arms alternated in one session, so the session effect seen before (whole batches going one way) is controlled for. Tonight's boots were in the "too bright" state: every control went bright.
  - Fisher test (a standard test for small yes/no counts), main runs 3/3 against 0/4: p = 0.03 one-sided. With the extras, 4/4 against 0/5: p = 0.008.
- **It costs about 20% fps everywhere after the door.** Read sync is 16% slower at the door and 19% slower in the village and fly-over. After the cut it is 25-27% slower. **It is not shippable as it is.**
- **The check mode shows the bytes the game reads almost never change.** The read's own bytes changed in 3 of about 38,000 synced reads:
  - two in the house load (a small counter going 4 → 6 → 8);
  - one in the 10 s window that holds the greeting cut. Its address was not logged, because the 8 detail lines of that window were already used up.
  So the fix works, but the counters cannot yet say whether it works by handing over that one right number or by the timing: the CPU now waits about 68 times a frame.
- Cheapest design the counters support: **arm read sync only from the start of a black frame to about 1.5 s after it ends.** Details in section 6.

## 6. Verdict

- **Does read sync fix the too-bright second? Yes.**
  - 3 of 3 controls against 0 of 4 read-sync runs (4 of 4 against 0 of 5 with the extras), interleaved in one session that was in the "too bright" state. The curves and the frames agree.
  - How sure: fairly sure for this session state (p 0.03 main, 0.008 with extras). It also fixes the fade order (1 of 3 controls out of order) and the one-frame light dip in the village (3 of 4 against 0).
  - Not yet seen: a warm-store session. A session where controls are clean cannot show a gain, but it would show the cost alone.
- **Is the cost acceptable? No, not as it is.**
  - It is −21% over the walk and −16% at the door, the best case. After the cut it is −27 to −31%. That is about 20% or more nearly everywhere.
  - It is far more than the half-fps budget agreed for putting the guard in the play settings. A clean picture at −21% is roughly what the full wait gives, so the fast settings lose their point.
  - Read sync is a candidate as proof of cause, not as a play setting.
- **What would make it cheaper.** The counters show the cost is flat: about 68 syncs every frame for the whole session, with no burst at the cut. Almost none of them change the bytes read (3 of 38,016). Ranked:
  1. **Cheapest the counters support today: time-box it.** Arm read sync at a present that shows a black frame, keep it on through the black and about 1.5 s after it ends, then off. It is already a live switch that changes at a present, so it can be flipped from there.
     - The too-bright curve lasts 0.7-1.0 s after the black, and the one changed read was in the window holding the cut.
     - Cost: about 1.5-2.5 s at −20% per cut or load, zero in play.
     - It works whichever way the fix works (the one read, or the timing), because that window gets the same treatment as tonight's runs.
     - It needs a cheap black test at the present: lever 2 in `drafts-2026-11-11/guard-door/understand-evidence.md`, a 1x1 average of the swapchain image (the picture about to be shown).
     - Risk: a read that sets the exposure before the black starts would be missed. Test: the door walk with read sync time-boxed, 3+3 interleaved, cut verdict plus fps by window.
  2. **Then narrow it to the one range.** Change check mode to log every read whose own bytes changed. There are only about 3 a run, so the 8-line cap does not need to apply to them.
     - One check-mode door walk then names the address that changes at the cut. Read sync could then cover only that range, about 1 read a frame instead of 68.
     - Only do this if the time-boxed test passes. If the fix turns out to be timing and not that read, a range-only sync would not fix the picture.
  3. **A cap on syncs per frame is not supported.** No counter says which of the 68 reads matters, so a cap would drop reads blindly.
  - Separately, the 94-95% escape rate means most waits do not get the frame they were meant for. Raising the escape from 2 ms would cost more, not less, so leave it as is for the time-boxed version.
