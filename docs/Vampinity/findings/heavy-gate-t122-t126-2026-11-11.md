Terms, one line each:
- **back thread**: the GPU thread that turns the game's draw commands into Vulkan work; at this spot it sets the pace.
- **front thread**: the GPU thread that reads the game's command stream and hands it to the back.
- **back idle**: ms per second the back had nothing to do (from the 10 s `GPU split per second` line).
- **ring words**: command words the front passed to the back per second; per frame it measures how much the view asks for.
- **back ns per word**: (1000 - back idle) / ring words: the back's busy time per command word, my own measure of its speed.
- **DMA miss**: the front had to wait for the back to finish before it could read a value the game asked for.
- **p99 frame time**: the phase line's "1% low": 99 of 100 frames were at least this fast.
- **dip phase**: a 20 s phase with back idle over 175 ms/s and about 1 fps low; seen on both builds; the GPU set the pace for a few seconds.

## Short answer

- **No loss beyond the noise.** Back to back, T126's two starts (16.77 / 17.49 fps) sit between the four T122
  starts around them (17.74 / 16.87, then 18.01 / 17.51). Raw: T126 minus T122 = **-0.40 fps** (all phases),
  **-0.44** without dip phases. But the T122 starts span **1.14 fps** among themselves, and the T122 mean rose
  **+0.46** from leg 1 to leg 3. Two T126 starts cannot separate -0.4 from 0.
- **Most of the gap is the camera.** The steered walk stops at slightly different angles. How much the view asks
  for (ring words per frame) explains T122's own spread almost fully (r = 0.96 over six T122 starts). Corrected for
  it: **-0.13 fps back to back** (two-sided range +0.14 to -0.39), **-0.23 fps with all ten starts of the day**
  (-0.02 to -0.42). In the frames, T126 never landed in the low, close camera pose that gave T122 its 17.9-18.0
  starts. Starts with the same pose: +0.13 and -0.32.
- **Honest range for T126 minus T122 at the heavy spot: 0 to -0.4 fps, best guess about -0.2 (about 1%).**
- **What moved, if anything: the back's time per command word**, +1.8% over the whole day (210.3 against 206.5 ns),
  but only +1.0% back to back (208.3 against 206.3), inside T122's own range (203.5-209.5). Front wait per DMA miss
  did **not** move back to back (94.1 / 99.0 us against 94.1-103.4 on T122). Back idle did not move.
- **Patches:** none of 0557-0565 does more than read a flag when its switch is off. The busiest one is 0557: every
  register method on the back (about 2 million a second) now first calls `IsL974NeutralMethod`, which reads the
  L974 switch, before the fast-draw check. Size: about 1-2 ms a second of back time, about 0.1-0.2% (INFERRED).
  It is cheap to remove anyway (below).
- **Village gate (fixed view, no steering):** T120 22.29 / 22.28, T122 22.72 / 22.46, T126 22.83 / 22.06.
  T126 minus T122 -0.14, T126 minus T120 +0.16. The gaps between two starts of the same build reach 0.77. **Level.**
- **Verdict:** T128 / T129 built on T126 **can be release candidates on speed grounds**. No loss has been shown. A
  loss of up to about 0.4 fps (2%) at the heavy spot is not ruled out. A fixed-view heavy gate would settle it.
- No crash, no device lost, every run `script_end`, steer 13/13 in all ten heavy runs.

## 6. Verdict

Back to back, T126 stood 0.4 fps under the four T122 starts around it. That is less than the 1.1 fps between T122's
own starts and about the same as T122's +0.46 drift from leg 1 to leg 3. Most of it follows the camera pose the
steered walk happened to stop at: T126 never got the low, close pose that gave T122 its 17.9-18.0 starts. Corrected
for how much each view asks of the back, T126 is 0.1-0.2 fps lower (range 0 to -0.4). The village gate, whose view
never changes, shows T126 level with T122 and T120. With every switch off, no patch does more than read a flag. The
largest of these reads, 0557's in `ProcessMethodCall`, comes to about 0.1-0.2% of the back. **So a build based on
T126 (T128, T129) can be a release candidate on speed grounds: no loss has been shown.** What is not shown is that
the cost is exactly zero. A loss of up to about 2% at the heavy spot fits the data, and the back's time per command
word leans the same way (+1-2%, inside the noise). Before a speed claim against T122, run the fixed-view check below.
In the meantime, take 0557's switch read out of the per-method path (one line, same behaviour).

## What would settle it

1. **A heavy gate with a fixed view:** a save already standing at the tunnel mouth, or a scripted camera reset after
   the steer, so the pose is the same every start. Then T122, T126, T122, T126 (ABAB, 3 starts each). With the
   pose fixed, T122's spread should drop from about 1 fps to about 0.3, the gate's level, and a 0.2 fps cost would show.
2. If the pose cannot be fixed: 4+ starts per build in ABAB order, and judge by back ns per command word (no pose
   needed), with `EDEN_UP_UBO_BIND_TRIM` stats or a per-draw counter on in both, to log draws per frame.
3. If a cost shows: one profile pair (`EDEN_NX2_GPU_PROFILE=1`, T122 against T126, same pose) to see which zone
   grew. Check `register methods` first (0557) and `configure` (0559).
